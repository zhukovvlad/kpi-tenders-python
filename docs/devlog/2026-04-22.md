### Что сделано

**1. Базовый scaffolding (FastAPI + Celery)**

Сервис поднят с нуля по ТЗ из `PROMPT.md`. Структура пакетов зафиксирована под будущие 4 модуля:

```
app/
├── main.py               — FastAPI factory + логгер
├── celery_app.py         — Celery + Redis, task_routes, task_default_queue
├── config.py             — Pydantic Settings, lru_cache get_settings()
├── api/                  — routes.py, schemas.py
├── workers/              — router.py, base.py + 4 task-файла
├── parsers/ nlp/ llm/    — placeholder-пакеты для будущих модулей
├── storage/minio_client.py
└── go_client/client.py
```

`venv` на Python 3.12 (на WSL `python3.10-venv` недоступен без sudo).

**2. FastAPI endpoints**

- `POST /process` — принимает `ProcessRequest{task_id, document_id, module_name, storage_path}`, вызывает `dispatch()`, отвечает `202 Accepted` с `celery_task_id`
- `GET /health` — проверяет Celery через `control.ping(timeout=0.5)`, возвращает `{"status": "ok", "celery": "ok"|"degraded"}`

Валидация входа — Pydantic; `module_name` — `Literal["convert", "anonymize", "extract", "parse_invoice"]`. Неизвестный модуль → `ValueError` в диспетчере → `HTTP 400`.

**3. Celery + очереди `io` / `llm`**

Ключевое решение: задачи разнесены по двум очередям по профилю нагрузки.

| Очередь | Задачи | Почему |
|---|---|---|
| `io` | `convert`, `parse_invoice` (XLSX-ветка) | I/O-bound парсинг, можно scale'ить concurrency |
| `llm` | `anonymize`, `extract`, `parse_invoice` (PDF через Gemini — туда же по факту) | Тяжёлые модели/LLM — низкий concurrency, чтобы не забивать RAM/rate-limits |

Роутинг через `task_routes` в `celery_app.py` — модуль-код о маршрутизации не знает. `task_default_queue = "io"`. Конфиг воркера: `task_acks_late=True`, `worker_prefetch_multiplier=1` — задача остаётся в очереди до ACK, воркер берёт по одной (важно для long-running LLM).

**4. Общий lifecycle задач (`workers/base.py`)**

Вынесен единый каркас `run_document_task(task, task_id, document_id, storage_path, handler)`:

```
processing → minio.download(storage_path) → handler(bytes, path) → completed
                                                                 → failed (retry)
```

Модульный `_handle()` — чистая функция, ничего не знает про HTTP/брокер. Ретраи: 3 попытки, `default_retry_delay=30` с. Если отчёт в Go падает на failure-пути, логируется, но не маскирует исходное исключение — `raise task.retry(exc=exc) from exc`.

**5. MinIO client**

`MinIOClient.download(storage_path) -> bytes`. Парсер `parse_storage_path()` принимает оба формата:
- `bucket/prefix/uuid.ext` (явный bucket)
- `prefix/uuid.ext` (дефолтный `MINIO_BUCKET`)

Тип файла определяется по расширению `storage_path`, не по MIME — требование ТЗ.

**6. Go client с ретраями**

`GoClient.update_task(task_id, status, ...)` — `PATCH /internal/worker/tasks/{id}/status` с `Authorization: Bearer <SERVICE_TOKEN>`. `tenacity` ретраит **только** `NetworkError | TimeoutException | RemoteProtocolError` (3 попытки, экспоненциальный backoff 0.5 → 4 с). 4xx/5xx — `GoClientError` без ретрая.

### Принятые решения

- **Celery только на Python-стороне.** Go не знает про Celery-протокол, общается только через HTTP (`POST /process`). Redis — общий брокер, но разговаривает с ним только Python. Это изолирует Go от внутренней реализации воркера: смена очереди/брокера на Python-стороне не требует изменений в Go.
- **Две очереди `io` / `llm`, а не одна.** Парсинг DOCX/XLSX в миллисекунды vs. запрос к Gemini на десятки секунд. Общая очередь привела бы к head-of-line blocking: LLM-задачи блокировали бы быстрый парсинг. Отдельные воркеры (`make worker-io` + `make worker-llm`) масштабируются независимо. В dev — единый `make worker` на обе очереди для простоты.
- **`task_acks_late=True` + `worker_prefetch_multiplier=1`.** Если воркер упал во время LLM-запроса, задача вернётся в очередь, а не потеряется. Prefetch=1 не даёт воркеру "захватить" пачку задач и держать их в памяти.
- **Общий lifecycle в `workers/base.py`, а не декоратор.** Декоратор Celery уже применён к задаче (`@celery_app.task`), наслаивать второй декоратор с `bind=True` — запутанно. Явный `run_document_task(self, ..., handler)` проще читать и тестировать (handler — чистая функция, тестируется без Celery).
- **Ruff вместо black + isort + flake8.** Одна зависимость, одна конфигурация, кратно быстрее. Совместим с black по форматированию.
- **`default: help` в Makefile.** `make` без аргументов не запускает dev-сервер (опасный default), а показывает справку. Заимствовано из `parser_tender_xlsx`.
- **`Makefile.local` в `.gitignore`.** Позволяет каждому разработчику держать свой `HOST`/`PORT`/`CELERY_LOGLEVEL` без правки shared Makefile и без конфликтов в PR.
- **Тип файла по расширению `storage_path`, не по MIME.** Требование `PROMPT.md`. MIME от MinIO может отсутствовать/врать (`application/octet-stream` для DOCX); расширение — источник истины.
- **Retry только на сетевые ошибки в Go client.** 4xx/5xx — это осознанный ответ Go, ретрай только усугубит (например, при 422 валидации). Сетевые сбои — да, экспоненциальный backoff 0.5 → 4 с.
