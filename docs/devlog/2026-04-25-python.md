## Решения и обоснования

**Почему убрали HTTP, а не оставили как есть.**
Python API (`/process`) был прокси-слоем: принимал HTTP от Go и вызывал `apply_async`. Если воркеры недоступны — это нормально (Celery держит очередь), но если сам Python API недоступен — Go не мог поставить задачу вообще. Redis видят оба сервиса, поэтому Go публикует напрямую, минуя этот лишний hop.

**`/health` остался.**
Python API не исчез полностью — он нужен для мониторинга состояния воркеров (`celery ping`). Это единственная причина держать FastAPI-процесс запущенным рядом с воркерами.

**Формат: Celery protocol v2 через LPUSH.**
Celery использует Redis-список: producer — `LPUSH`, worker — `BRPOP`. Сообщение — JSON с base64-кодированным `[args, kwargs, embed]` в поле `body`. Go-агент реализовал это в `internal/pythonworker/client.go`; в `headers.id` пишется Go-шный UUID задачи, что даёт сквозной трейсинг без дополнительной логики.
